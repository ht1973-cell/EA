# ⑦-2 TTS品質ゲート（発音誤り・ノイズ混入の恒久対策）

EP01の制作中に発生した「TTSの誤読」「長文一括生成によるノイズ混入」を、
**その場しのぎの手直しではなく、シリーズ全52本に効く構造的な仕組み**として
組み込んだもの。以後、新しいエピソードでもこの仕組みが自動的に働く。

## 発生した問題と原因

1. **数字の誤読**：「十八」をTTSが『じゅうばち』と連濁誤読（本来「じゅうはち」）。
2. **専門用語の誤読**：「貯金」をTTSが『じょきん』と誤読（本来「ちょきん」）。
3. **長文一括生成によるノイズ**：SC001〜SC005を1回のTTS呼び出しで連結生成すると、
   確率的に日本語以外の音や不自然なノイズが混入することがあった。

## 恒久対策（コードとして実装済み）

### 1. 数字読み上げの自動変換（`pipeline/lib/tts_numbers.py`）

漢字圏の数詞読み上げ（百・千の連濁規則を含む）を、TTSのG2P任せにせず
**決定的なアルゴリズム**として実装。算用数字（20万円）と漢数字（十八）の
混在表記にも対応する。「その単語だけ人間が気づいて直す」運用から、
「数字が出てきたら常に正しく変換される」構造へ変えた。

```python
from tts_numbers import number_to_yomi, normalize_numbers_for_tts
number_to_yomi(18)        # -> 'じゅうはち'
number_to_yomi(200000)    # -> 'にじゅうまん'  (=20万)
normalize_numbers_for_tts("十八パーセント")  # -> 'じゅうはちパーセント'
```

### 2. 専門用語の誤読辞書（`pipeline/lib/tts_homographs.json`）

52本シリーズで繰り返し登場する金融用語（貯金・相続・積立・控除 等）の
誤読しやすい読みを辞書化。新しい誤読が見つかったら、この辞書に1行足す
だけでシリーズ全体に反映される（1話ずつ手直し不要）。

### 3. narration→tts_prompt の自動生成（`pipeline/lib/tts_lint.py`）

台本の`narration`（画面表示用の正しい漢字）から、上記2つを適用した
`tts_prompt`（音声合成専用の開き読みテキスト）を自動生成する。
`run_ep01.py --stage build` は、`tts_prompt`が未設定なら自動的にこれを
生成して使う。**台本作成時に人間が発音を気にする必要をなくす**のが狙い。

### 4. 長文一括生成の禁止（構造ルール）

**1回のTTS呼び出しには1シーン分の短い文だけを渡す。**
複数シーンを連結した長文を1回で生成すると、モデルが確率的にノイズ・
幻聴的アーティファクトを混入させるリスクが上がることを確認した。
`prompts/A7_voice.md`にこの禁止事項を明記し、A7（音声生成）は必ず
scene単位で呼び出す設計に統一した。

### 5. 生成後の異常検知＋自動アボート（`run_ep01.py` stage_build内）

実ナレーション音声を`voice/`に配置してビルドすると、
「文字数から想定される尺」と「実測の尺」を自動で突き合わせる
（`tts_lint.check_duration_anomaly`）。無音stub（プレースホルダ）は
検査対象外（`wav_is_real_narration`で実音声か判定）。

大きく乖離していた場合＝ノイズ混入や幻聴的アーティファクトの疑いとして、
**最終動画への焼き込みをその場で中止**する（例外を送出してbuildを止める）。
検査結果は`qa/EP{ep}_voice_anomaly_report.json`に必ず保存され、
QA工程（`voice_anomaly_check`）にも反映される。

> 動作確認済み：意図的に25秒の異常音声を仕込んでbuildを実行したところ、
> 「尺が長すぎる疑い」を検知してbuildが例外で停止することを確認した。

## 未解決・既知の限界

- **音声認識（ASR）による発音の自動検証はできない**。この環境にはそのような
  ツールがなく、最終確認は人間の試聴に依存する。異常検知（4・5）はあくまで
  「尺の統計的な乖離」を代理指標にした間接的な検知であり、完璧ではない。
- **テキスト正規化では直らない、TTSエンジン自体の音響的な癖がある**。
  例：ひらがなで「じゅうはち」と入力しても、一部エンジン（MiniMax）は
  「じゅうばち」と連濁して発音することを確認した。この場合の対策候補：
  - カタカナ表記に変える（G2Pパスを変える）
  - 別の音声エンジン（seed_speech等）にフォールバックする
  - 数値表現自体を言い換える（意味を変えない範囲で）
  どれが有効かはケースバイケースで試聴確認が必要。有効だった対策は
  `pipeline/lib/tts_lint.py`のコメント、または本ドキュメントに追記していく。

## 今後の運用ルール

1. 新しいエピソードの台本を作る際、`narration`だけ書けば`tts_prompt`は
   自動生成される（手動で開き読みを書く必要はない）。
2. 誤読が報告されたら、まず`tts_homographs.json`か`tts_numbers.py`で
   直せないか検討する（テキスト側の問題か、エンジン側の癖かを切り分ける）。
3. テキスト側で直らない場合は、本ドキュメントの「未解決」セクションに
   ケースを追記し、エンジン切り替え等の対策を試す。
4. 長文一括生成は今後も禁止。scene単位の生成を徹底する。
